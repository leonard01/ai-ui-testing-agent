# Persistent execution history

The local Review UI keeps completed Playwright test reports and suite summaries available **after restarting the review server**. Nothing is uploaded to a hosted service or regenerated by an AI model when you open an old report.

## How to use

1. Start the local review server with `npm run build && npm run review`.
2. Execute an approved test or a suite from **3. Execute and diagnose**.
3. Open **Execution history** to inspect the completed runs and suites. You can refresh the list without rerunning anything.
4. Choose **Open previous run** to see the original steps, expected/observed values, diagnosis and available screenshot/trace links. Choose **Open previous suite** to see its consolidated verdict and navigate to its member runs.
5. Stop and restart the server: the same completed results will load automatically from disk.

The history view includes up to the 100 most recent individual runs and 20 most recent completed suites per server session. It sorts by recorded start time. A suite's member runs are also visible as individual entries, marked as *suite member*.

## Storage

For the default review server, the existing output location remains `run-results/`. When you start a review server with a custom `outputDir` (as the automated tests do), results are beneath `<outputDir>/run-results/`.

- `run-results/<run-id>/report.json` is written by the existing deterministic runner.
- `run-results/<run-id>/failure.png` and `trace.zip` remain available when the runner captured failure evidence.
- `run-results/<run-id>/run-metadata.json` now stores the saved test filename, start time and optional suite association or runner error.
- `run-results/suites/<suite-id>/report.json` contains the consolidated completed-suite snapshot.

On startup the server reconstructs the history from these files, including legacy `report.json` files that predate the metadata sidecar. Older reports without a saved filename appear as unassociated. No database, cloud service or API key is required.

## Reliability, bounds and limitations

- Only **completed** records are restored. If a server dies while executing a test or suite, its interrupted execution is not treated as a pass. A completed member report can still be inspected if its suite snapshot was never finalized.
- Files with invalid paths, incomplete or corrupted report JSON, and unfinished suite snapshots are ignored.
- History records **previous execution results**, not the current state of the web application. Opening one does not rerun tests or re-verify assertions.
- History is **locally stored**, not an immutable compliance audit. The current approved-test replacement/repair workflow intentionally deletes older runs associated with the superseded test, including their screenshots and traces. Other completed history remains until the user manually cleans the results folders. A future audit-log milestone could retain superseded revisions instead.
- History entries loaded in memory are bounded to 100 runs and 20 suites, but files on disk are **not automatically deleted** when these limits are reached. They may grow over time; manually clean older files if storage is limited.
- A restored history run has its original report and file artifacts, but short-lived DOM inspection evidence in process memory is not reconstructed. Existing repairs that depend on that transient DOM index may require a fresh test run.
- The UI does not yet support filtering/searching results, trending historical failures, exporting a combined report or comparing historical test revisions. These are future enhancements.

## Verification

Integration coverage creates passing and deliberately failing approved tests, runs them and a two-test suite, closes the local server, recreates it with the same output directory and checks report/detail/trace access and UI drilldowns. Separate tests verify that interrupted, corrupt and unrelated output folders cannot masquerade as completed runs.
